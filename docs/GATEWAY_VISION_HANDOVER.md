# Gateway Handover: Fix `[unsupported image]` Confusion

## Problem

When a user uploads an image to a **non-vision model** (e.g. `deepseek-flash-chat`), the Gateway currently does two conflicting things:

1. **Replaces the image with `[unsupported image]`** in the messages array sent to the model
2. **Auto-generates a vision analysis** via `task: 'vision'` and injects it into the assistant response with prefix: `📷 **MCP Vision Analysis:**\n[Image 1 (filename)]:\n## Analysis\n\n...`

This confuses the LLM because:
- It sees `[unsupported image]` in the user message → thinks "there's an image I can't see"
- It has MCP vision tools available → tries to use them
- It doesn't realize the analysis was already auto-generated by the Gateway
- Result: redundant tool calls (`vision_create_session` → `vision_analyze` again, plus confused exploration like `browser_session_list`, `memory_recall`)

## Evidence

**Conversation log (`convo.json`):**
- Exchange 1: User sends image + "What do you see?"
- Exchange 1 assistant: Already contains full vision analysis (Gateway-injected)
- Exchanges 2-7: LLM makes redundant tool calls including `browser_session_list`, hallucinated URL `https://i.imgur.com/placeholder-vlcsnap.png`, etc.

**Server log (`logs/2026-05-15-15-53-16-gw-73juqv.log`):**
```
15:56:53 vision_create_session with actual image_data (861KB) → success
15:56:53 vision_analyze → gets analysis
15:57:01 memory_recall + browser_session_list
15:57:07 vision_create_session with hallucinated URL "https://i.imgur.com/placeholder-vlcsnap.png"
15:57:10 vision_list_sessions
15:57:11 vision_get_session
15:57:14 vision_analyze again (follow-up query)
```

## Root Cause Location

The Gateway's **message preprocessing / adapter formatting logic** — specifically the code path that:
1. Detects a model lacks `capabilities.vision`
2. Replaces `type: "image_url"` content blocks with placeholder text
3. Simultaneously routes the image to a vision model for auto-analysis
4. Prepends the vision result to the assistant response

## Required Fix

When the Gateway auto-analyzes an image for a non-vision model, **do NOT emit `[unsupported image]`** in the user message. Instead, replace the image content block with a clear text indication that the image was already processed.

### Recommended approach

Replace the image content block in the user's message with:

```json
{
  "type": "text",
  "text": "[Image attached: filename.png — vision analysis has been performed and is shown above]"
}
```

Or inline the analysis directly into the user message context:

```json
{
  "type": "text",
  "text": "[Image attached: filename.png]\n\n**Vision Analysis:**\n[auto-generated analysis text here]\n\nThe user's original message was: 'What do you see?'"
}
```

### Key principle

The LLM must understand that **the image has already been analyzed** so it does not attempt to use MCP vision tools redundantly. The `[unsupported image]` text actively signals the opposite — that the image is unhandled.

## MCP Server Changes Already Made

The orchestrator side was also tightened to reduce confusion:

- `vision_create_session` description now says: *"BEFORE calling this, check `vision_list_sessions` — if a session already exists for this image, reuse it"*
- `vision_get_session` now prominently displays: *"**This image has already been analyzed N time(s).** Only call `vision_analyze` again if the user asks for more detail"*
- `browser_session_list` description now explicitly distinguishes browser sessions from image sessions
- `fetchImageAsBase64` detects hallucinated placeholder URLs and returns helpful error messages

But these are mitigations. **The primary fix belongs in the Gateway's message formatter.**
